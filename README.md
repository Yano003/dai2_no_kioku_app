## アプリ名を変更する手順

アプリ名は確定前のため（要件定義書 11.2 No.8）、**3箇所を同じ値に揃えるだけ**で
変更できるようにしている。Dart から OS のアプリ一覧に出る名前を設定することは
できないため、ネイティブ側にも同じ文字列が必要になる。

| # | ファイル | 変更する箇所 |
|---|---|---|
| 1 | `lib/core/app_identity.dart` | `AppIdentity.displayName` |
| 2 | `android/app/src/main/res/values/strings.xml` | `<string name="app_name">` |
| 3 | `ios/Runner/Info.plist` | `CFBundleDisplayName` |

画面内の表記はすべて `AppStrings.appName`（= `AppIdentity.displayName`）を
参照しているため、①を変えれば追随する。タグラインも同じく `AppIdentity.tagline`。

> **パッケージ名（`jp.co.hitokoto.kiokuwo`）は別物**で、ストア公開後は変更できない。
> 表示名の変更に引きずられて変えないこと。なお、ヒトコト株式会社様の実ドメインが
> `hitokoto.co.jp` と異なる場合は、**初回申請前に**
> `android/app/build.gradle.kts` の `applicationId` / `namespace`、
> `ios/Runner.xcodeproj/project.pbxproj` の `PRODUCT_BUNDLE_IDENTIFIER`、
> `android/app/src/main/kotlin/.../MainActivity.kt` の `package` を揃えて変更する。

### 内部の Dart パッケージ名について

`pubspec.yaml` の `name:` は `dai2_no_kioku` のまま残している。これは
**利用者にもストアにも一切露出しない内部名**で、影響範囲は `pubspec.yaml` と
テストの `package:` import だけ（`lib/` は全て相対 import のため無関係）。

改名する場合はプロジェクトのディレクトリ名も併せて変えるのが自然で、
ビルドキャッシュの作り直しを伴う。動作確認の区切りで別途まとめて行うのが安全。

## 文言の差し替えについて

**利用者の目に触れる文言はすべて `lib/core/app_strings.dart` に集約している。**
画面側に文字列リテラルを直接書かないこと。確定文言のご提供後、このファイル1枚の
差し替えで全画面に反映できる（要件定義書 10章 前提5・6）。

各定数には文字数の上限の目安をコメントで付記している。確定文言が想定より長いと
レイアウトが崩れ、差し替え1回の枠に収まらなくなるため、事前に文字数を合意すること。

## 既知の制約・技術メモ

### 画面イメージとの差分（要ご確認）

ゴールデン画像で突き合わせた結果、残っている差分は次の2点。

**1. 予定の各行に鉛筆ボタンを置いている**

画面イメージのリストは ☐ と予定名だけだが、S-07 修正画面への導線が
他に無いため独立したボタンとして追加している。長押しに割り当てると
対象利用者には気づけないため、あえて見える形にした。
画面イメージどおりの清潔さを優先するなら、別の導線を検討する。

**2. 前後のカードをわずかに小さく表示している**

要件定義書 4.5 の「上下に前日・翌日のカードがうっすら見える」は、
画面イメージでは**前後のカードの端が覗いている状態**として描かれており、
文字は薄くなっていない。そこで色はほぼ落とさず、少し縮めることで
中央のカードを主役にしている。「薄く」の解釈が異なる場合は調整する。

### 繰り返し予定の上限判定は「基準日」で行っている（要ご確認）

1日5件の上限（2.2）は、登録しようとしている日の件数で判定している。
繰り返し予定（毎日・毎週）は将来の多数の日に発生するため、そのすべてを事前に
検査すると「毎日の予定を1つ増やすだけで、遠い先の1日が埋まっているという理由で
登録できない」という不自然な挙動になる。

そこで **登録時は基準日だけで判定し、表示側で5件に丸める**構成にしている。
繰り返しが重なって6件以上になる日はカードに5件だけ表示され、溢れた件数は
`DayCard.hiddenCount` に入る。

この扱いでよいか、溢れた分を利用者に知らせるべきかをご確認ください。

### S-01 の許可取得が「3段階」ではなく「2段階」になっている（要ご確認）

要件定義書 4.1 では「マイク・音声認識・通知の利用許可を1つずつ順に取得する」と
あるが、**マイクと音声認識の許可は OS 側が1回の呼び出しでまとめて要求する仕様**で、
アプリから分割できない（iOS は2つのダイアログが連続して出る／Android はマイクのみ）。

そこで「声を使うこと」と「お知らせ」の2段階にしている。ダイアログを分割できない以上、
段階を増やすと説明だけの画面が挟まることになり、「初回起動が最大の離脱点」という
設計上の注意にかえって反するため、この形が要件の意図に沿うと判断した。

### S-08 で起床・就寝を変えると通知時刻も追随する（要ご確認）

要件定義書 4.8 は「通知時刻の変更」と「起床・就寝の時刻の変更」を並列に挙げているが、
両者の関係が書かれていない。本実装では**起床・就寝を変えると通知時刻も30分前に
合わせて変わる**ようにしている（変更が同じ画面上ですぐ見えるため予測しやすく、
追随させないと「いつもの時刻を変えたのに通知が変わらない」という食い違いが起きるため）。
通知時刻だけを個別に決めたい場合は、そのあとで通知時刻を直接変更できる。

### permission_handler は使わず app_settings を使っている

`permission_handler_android` 14.0.0 は `compileSdk = 37` を要求するが、
Android SDK 側のプラットフォーム名がマイナー版付き（`android-37.0`）に変わっており、
Gradle が探す `android-37` が存在せずビルドが失敗する。

許可の取得自体は speech_to_text（マイク・音声認識）と
flutter_local_notifications（通知）がそれぞれ持っているため、permission_handler は不要。
S-08 の「端末の設定を開く」には、より軽量な `app_settings` を使っている。

### 通知の精度について

Android は端末の省電力機能により、設定時刻から数分〜十数分遅れる、または
メーカーによっては届かないことがある（要件定義書 6.3）。
`AndroidScheduleMode.exactAllowWhileIdle` と `USE_EXACT_ALARM` で最大限の精度を狙うが、
100%の保証はできない。

### 通知タップで開くカードの日付

前日夜の通知をタップしたときは、当日のカードを挟まずに**翌日のカード**を開く。
開く日付は通知に payload（`card:2026-08-20`）として持たせている。

この受け渡しは Android の Activity の起動方式に影響される。
`AndroidManifest.xml` の `MainActivity` は **`launchMode="singleTask"`** にしてある。
Flutter の既定（`singleTop`）のままだと、タスクが履歴に残ったままプロセスだけが
終了している状態でタップした場合に payload が捨てられ、通常の起動と区別が付かなく
なる（＝今日のカードから始まってしまう）。理由の詳細は AndroidManifest.xml の
コメントに記載している。**この行は変更しないこと。**

受け渡しの様子は `adb logcat -s flutter` で `[通知]` を含む行として確認できる。

### 通知の事前予約

ローカル通知は予約した時点で内容が固定される。文面自体は予定の有無によらず
「こんばんは／明日の安心カードを確かめましょう」で共通だが、タップして開くカードの
日付は日ごとに違うため、1日分ずつ予約する必要がある。
このため、**アプリ起動時と予定の登録・修正・削除のたびに14日先までを予約し直している**
（`NotificationService.rescheduleAll`）。長期間アプリを開かないと予約が尽きるため、
起動時の再予約は省略できない。

前日夜の通知をタップしたときに開くのは**翌日のカード**（`PlannedNotification.cardDate`）。
当日のカードを挟まない。（お客様ご指摘 2026/08/17）
